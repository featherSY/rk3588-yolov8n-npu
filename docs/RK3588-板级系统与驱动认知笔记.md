## 0. 一句话总览（人话版）

**一次推理，就是「叫 NPU 这个工人干一次活」。** 这份输出把工人从登记、发工牌、通电、调速度、搬材料到最后干活，全链路查了一遍。

| 环节 | 大白话 | 板上的实物 | 输出里的证据 |
|---|---|---|---|
| ① 出厂说明书 | 板子上有什么、接在哪、能跑多快 | 设备树 dtb | `model = Firefly AIO-3588Q`；`npu@fdab0000`、`npu-opp-table`、`npu-thermal` |
| ② 开机登记 | 内核按说明书把工人登记进系统 | U-Boot → kernel 6.1.118 | cmdline 里 `androidboot.fwver=ddr…,bl31…,bl32…,uboot…` |
| ③ 正式编制 | 工人是**编进内核**的，不是临时工 | `CONFIG_ROCKCHIP_RKNPU=y` | 所以 `lsmod` 查不到、`modprobe -r` 被拒 |
| ④ 发工牌 | 用户态凭工牌找工人 | DRM render node | `renderD129`（226,129），**没有** `/dev/rknpu` |
| ⑤ 搬材料 | 模型权重走专用内存通道 | DRM GEM / CMA / IOMMU | `CONFIG_ROCKCHIP_RKNPU_DRM_GEM=y`、`DMA_HEAP is not set`、CMA 288 MB |
| ⑥ 通电调速度 | 不干活断电，干活按档位升频 | devfreq + SCMI + power domain | 8 档 300M~1G；`pm_genpd` 四层全 `suspended` |
| ⑦ 干活 | 三核 NPU 执行推理 | `fdab0000.npu` | `NPU load: Core0/1/2: 0%`（空闲时） |
| ⑧ 摄像头那条线 | 有个窗口但没人接材料 | V4L2 / rkcif / rkisp | 47 个 v4l 节点；`-19 = -ENODEV` |

**最该记住的一句**：这块板跑的是 **基于 6.1 LTS 的 Firefly 厂商 BSP 内核（6.1.118，rk3588/firefly-6.1 分支）**，不是 kernel.org 的**主线 Linux（mainline）**。所以网上教程说「找 `/dev/rknpu`」在这块板上就是错的 —— 不是你配错了，是**厂家编译时选了另一套驱动形态**。

## 1. 这块板到底是什么

| 项 | 实测值 | 说明 |
|---|---|---|
| 板型 | `Firefly AIO-3588Q` | `compatible = "rockchip,aio-3588Q", "rockchip,rk3588"` |
| 内核 | `6.1.118 #9 SMP`（2026-04-29 编译） | 分支 `rk3588/firefly-6.1`，SDK `rk3588_linux6.1_release_20260428_v1.3.0f.xml` |
| 交叉编译器 | `aarch64-none-linux-gnu-gcc 10.3.1` | ARM 官方 A-profile 工具链，说明内核是**交叉编译**出来的 |
| 根文件系统 | Ubuntu 24.04.4 LTS | 内核是厂商 BSP、rootfs 是 Ubuntu，是典型的开发板组合 |
| 启动介质 | eMMC | `storagemedia=emmc`、`root=PARTLABEL=rootfs` |
| 调试串口 | `ttyFIQ0`，earlycon 在 `0xfeb50000` | 没有串口线就看不到早期启动日志 |
| 根文件系统叠加 | `overlayroot=device:dev=PARTLABEL=userdata,…` | 根目录是 overlay，`/etc` 下的改动能落到可写层 |

### 启动链（cmdline 里藏着的完整证据）

```
BootROM → DDR init (ddr-v1.19) → BL31 (ARM Trusted Firmware v1.51)
        → BL32 (TEE / OP-TEE v1.20) → U-Boot → kernel 6.1.118 → dtb 解析 → 驱动 probe
```

`androidboot.fwver=...` 这一串把 DDR 初始化固件、BL31、BL32、U-Boot 的版本全暴露了。cmdline 里还留着 `androidboot.*` 参数，说明这套 BSP 的 bootloader 是从 Android SDK 复用过来的 —— 这解释了「为什么一堆参数和 PC 上的 Ubuntu 不一样」。

`rcupdate.rcu_expedited=1 rcu_nocbs=all` 是厂商为实时性做的 RCU 调优；`irqchip.gicv3_pseudo_nmi=0` 关掉了 GICv3 伪 NMI。

> **面试可用的话**：「我这块板是 Firefly AIO-3588Q，跑厂家 6.1 的 BSP 内核，交叉编译工具链 10.3，Ubuntu 24.04 rootfs；启动参数里能看到 DDR/BL31/BL32/U-Boot 的完整固件版本链。」

## 2. 驱动形态：一锤定音

### 内核配置直接给了答案

```
CONFIG_ROCKCHIP_RKNPU=y              ← 编进内核（builtin），不是 .ko 模块
CONFIG_ROCKCHIP_RKNPU_DEBUG_FS=y     ← 所以 /sys/kernel/debug/rknpu/{version,load} 存在
CONFIG_ROCKCHIP_RKNPU_DRM_GEM=y      ← 内存走 DRM GEM
# CONFIG_ROCKCHIP_RKNPU_DMA_HEAP is not set   ← 不走 dma-buf heap
# CONFIG_ROCKCHIP_RKNPU_PROC_FS is not set
# CONFIG_ROCKCHIP_RKNPU_FENCE is not set
# CONFIG_ROCKCHIP_RKNPU_SRAM is not set
```

这六行把第三课的三个疑问一次说死：

1. **`lsmod | grep rknpu` 为空、`modprobe -r` 被拒** → 因为 `=y` 是 builtin，根本没有可卸载的模块。`/sys/module/rknpu` 里有条目（输出里那行 `rknpu` 来自这里，不是 `lsmod`），builtin 驱动也会有这个目录。
2. **`/dev/rknpu` 不存在** → 因为开了 `DRM_GEM`，驱动注册成 DRM 设备，节点是 `/dev/dri/renderD129`。
3. **换 `librknnrt.so` 没用** → 形态由内核决定，不由用户态库决定。

### 设备节点全貌

| 节点 | 主:次 | 属主 | 含义 |
|---|---|---|---|
| `card0` | 226:0 | root:video | GPU/显示主设备 |
| `card1` | 226:1 | root:video | 第二个 DRM card |
| `renderD128` | 226:128 | root:render | GPU 的 render node |
| **`renderD129`** | **226:129** | **root:render** | **NPU 的 render node**（`128 + minor 1`） |

`stat` 输出的 `major=e2 minor=81` 是**十六进制**：`0xe2 = 226`、`0x81 = 129`，和上面 `ls -l` 完全一致，不是另一种编号。

### 关于「为什么必须 sudo」

`getent group` 显示 `render:x:992:firefly,zsy`、`video:x:44:gdm,lightdm,firefly,zsy` —— **zsy 早就在两个组里了**。所以第三课那句推测（「加完组还失败、换 sudo 才好，怀疑 runtime 要读 root-only 的 debugfs 文件来判驱动形态」）现在得到了佐证：组权限不是瓶颈，`/sys/kernel/debug/rknpu/version` 这类 debugfs 文件的 root-only 才是。这一条在第三课里标注为「未 100% 证实」，现在证据更足，但仍不是内核源码级的证明，**表述时保留「推测」二字**。

### 库里为什么两种路径都有

```
strings /usr/lib/librknnrt.so → /dev/dri  /dev/dri/%s  /dev/rknpu
```

同一份 7.37 MB 的库（属主 `djw:zsy`，2025-06-10）**同时编译了两种驱动形态的探测逻辑**，运行时自动选。这也是「换库对性能无影响」的原因：换的是同一套逻辑的另一份二进制。版本字符串里最高到 `2.3.2`，与 `rknn-toolkit-lite2 2.3.2`、driver `0.9.8` 对齐。

## 3. 设备树：出厂说明书里写了什么

探查命中 31 个含 `npu` 的节点，展开了 8 个：

| 节点 | 内容 | 意味着什么 |
|---|---|---|
| `/pinctrl/npu/npu-pins` | `rockchip,pins` 二进制编码 | NPU 相关引脚的复用配置 |
| `/otp@fecc0000/npu-opp-info@55` | OTP 偏移 `0x55` 处的 OPP 体质数据 | **每颗芯片出厂烧了自己的频率/电压体质** |
| `/otp@fecc0000/npu-leakage@28` | OTP 偏移 `0x28` 处的 leakage | 漏电流/工艺偏差，用于调压 |
| `/npu-opp-table` | `operating-points-v2`；`nvmem-cell-names = leakage opp-info specification_serial_number customer_demand` | OPP 表**会读 OTP**，档位不是纯硬编码 |
| `/thermal-zones/npu-thermal` | `polling-delay=1000ms`、`passive=20ms` | NPU 有独立热区，每秒轮询 |
| `…/trips/npu-crit` | `temperature = 0x1c138 = 115000`（毫摄氏度 → **115°C**）、`hysteresis = 0x7d0 = 2°C` | 到 115°C 触发 critical，会强制降频/关机 |

**这一节最值钱的结论**：`npu-opp-table` 通过 `nvmem-cells` 引用 OTP 里的 `leakage` 和 `opp-info`，配合 `clk_npu_pvtm`（PVTM，工艺/电压/温度监测）和 `npu-thermal` 热区，构成一套**按芯片体质 + 温度动态调压调频**的闭环。你手动 `echo 1000000000 > userspace/set_freq` 做的事，本质是**绕过这套闭环、把频率钉死**，所以方差才从 101 ms 收到 46 ms。第三课「性能测量必须把所有频率锁死」从经验结论变成了有机制支撑的结论。

### 显示缺陷说明（不是文件坏了）

- 属性像 `'U   \x06'`、`'('`、`000003c2` 这样的输出是**二进制属性值**（phandle、`reg`、cell 数组都是 big-endian 字节），脚本按「可打印字符」判断时把 4 字节短二进制误当成字符串了。正确读法是用 hex，例如 `reg` 显示 `55 00 00 06` 对应 OTP 偏移 0x55、长度 6。
- `dtc` 没安装，所以导不出完整 `.dts`；`npu@fdab0000` 主节点落在「另有 23 个节点未展开」里，这次没打印出来。
- 这两点都不影响已有结论，但如果要写「设备树里 `reg`/`clocks`/`iommus` 具体值」，需要补一次定点 dump（见第 11 节）。

## 4. 内存路径：模型权重怎么进 NPU

| 证据 | 值 | 解读 |
|---|---|---|
| 内核配置 | `DRM_GEM=y`，`DMA_HEAP is not set` | 权重内存通过 **DRM GEM 对象**分配，不是 dma-buf heap |
| dmesg | `cma: Reserved 32 MiB at 0x100000000` | 0x100000000 = 4 GB 处预留的一块 CMA |
| `/proc/meminfo` | `CmaTotal 294912 kB (288 MB)`、`CmaFree 54812 kB` | **288 MB ≠ 32 MB**：说明设备树里配了多个 reserved-memory CMA 区（VPU/GPU/ISP 等各一份），dmesg 只 grep 到其中一行 |
| 启动日志 | `iommu: Default domain type: Translated`、TLB `strict mode` | SoC 上 IOMMU 全局开启 |
| 启动日志 | rkcif→group 17、rkisp→15/16、rga→2/3、mpp 各编解码器→1/4~14、vop2→18 | 多媒体 IP 各挂自己的 iommu group |
| 推理日志（第三课） | `gem name: 3, iommu domain id: 0` | NPU 侧确实走 GEM + iommu domain |

**链条**：用户态 `rknnlite` 提交模型 → `librknnrt.so` 通过 DRM ioctl 建 GEM 对象 → 内核从 CMA/系统内存分配页 → IOMMU 建立 NPU 可见的 IOVA 映射 → NPU 通过 DMA 直接读权重，无需 CPU 逐字节搬运。

> ⚠️ **待确认**：这次启动日志被 `head -25` 截断，没看到 `rknpu` 自己加入 iommu group 的那行；`gem name: 3, iommu domain id: 0` 来自推理日志。所以「NPU 挂在哪个 iommu group」暂不下定论，只说「NPU 侧存在 GEM + iommu domain」。

## 5. 时钟 / 电压 / 电源域：DVFS 三层

### 第一层：devfreq（策略）

| 项 | 值 |
|---|---|
| devfreq 设备 | `dmc`、`fb000000.gpu`、`fdab0000.npu`、两个 `rkvenc`、`fdd90000.vop` —— 六个 IP 共用 devfreq 框架 |
| NPU governor | `userspace`（我们手动设的） |
| 当前 / 最小 / 最大 | `1000000000` / `300000000` / `1000000000` Hz |
| 可用档位 | **8 档**：300 / 400 / 500 / 600 / 700 / 800 / 900 / 1000 MHz，每档 100 MHz |
| 可用 governor | 厂商私有的 `rknpu_ondemand`、`dmc_ondemand`、`vop2_ondemand`、`venc_ondemand` + 通用 `userspace/powersave/performance/simple_ondemand` |

### 第二层：clock（怎么真正改硬件频率）

`clk_summary` 里的 `scmi_clk_npu` 带 **SCMI 前缀** —— System Control and Management Interface，说明**主频不是 Linux 直接写 PLL 寄存器，而是通过 SCMI 让 BL31/ATF 固件去改**。这是 RK3588 这类 SoC 的常见设计。

其他相关时钟：`hclk_npu_root/hclk_npu0/hclk_npu2` 198 MHz（总线）、`hclk_npu_cm0_root/fclk_npu_cm0_core` 396 MHz（NPU 内部 CM0 微控制器）、`clk_npu_pvtm` 24 MHz（体质监测）、`tclk_npu_wdt` 24 MHz（看门狗）。

> 🔍 **一个极容易读错的点**：`clk_summary` 显示 `scmi_clk_npu` 是 **200 MHz 且 enable=0**，而 devfreq 说 `cur_freq=1000 MHz`。这不是矛盾 —— `cur_freq` 是 **devfreq 记下的目标 OPP**，即使硬件当前断电也保留上次设定；`clk_summary` 反映的是**此刻真实的时钟状态**，而此刻 NPU 电源域是关的（见第三层）。前者是「设定值」，后者是「实际值」。

### 第三层：power domain（供不供电）

```
npu (off-0)
└── nputop (off-0)
    ├── npu1  → /devices/genpd:1:fdab0000.npu  suspended
    └── npu2  → /devices/genpd:2:fdab0000.npu  suspended
        /devices/genpd:0:fdab0000.npu  suspended
```

四层电源域**全部 `suspended`/`off`** —— 这是 **runtime PM** 的直接证据：**不推理时内核把 NPU 整个断电，推理时才上电、升频、加载权重**。这解释了三件你之前观察到但没解释的事：

1. 首次推理明显慢（上电 + 升频 + 权重搬运）；
2. 不锁频时延迟在 73~101 ms 大幅飘（governor 反复升降频，叠加电源域唤醒）；
3. 为什么要 warmup 10 帧再计时。

### CPU 侧（顺带确认锁频仍生效）

| policy | CPU | 频率 | governor |
|---|---|---|---|
| policy0 | 0–3（小核） | 1800 MHz | performance |
| policy4 | 4–5（大核） | 2304 MHz | performance |
| policy6 | 6–7（大核） | 2352 MHz | performance |

三个 policy 全是 `performance`，NPU 是 `userspace@1 GHz` —— **说明板子从上次跑 demo 到现在没重启过，锁频仍然生效**。所以 `35.82 ms / 39.44 ms` 那组跨端数据确实是在锁频条件下测的，报告 §3.1 的测量条件成立。大核分成两组独立调频，两组频率略有差异（2304 / 2352 MHz）也符合体质分级。

## 6. V4L2：`-19` 到底是什么

| 项 | 实测 |
|---|---|
| `/sys/class/video4linux/` | **47 个节点**（含 `v4l-subdev*`） |
| `/dev/video*` | 之前查到的 41 个 —— 两个数字不矛盾，47 含 subdev，41 只数 `videoN` |
| subdev | `rockchip-mipi-csi2` ×2、`rockchip-csi2-dphy0/3`、`rkisp-isp-subdev` ×2 |
| video 节点 | `stream_cif_mipi_id0~3`、`rkcif_scale_ch0~3`、`rkcif_tools_id0~2` —— 反映 rkcif 的多通道硬件结构 |
| `media-ctl` / `v4l2-ctl` | **未安装**（`not found`）—— 是工具缺失，不是「没有拓扑」 |
| dmesg | `rkcif_update_sensor_info: get remote terminal sensor failed!` → `update sensor info failed -19` |

**`-19` 就是内核错误码 `-ENODEV`（No such device）**。机制是：V4L2 的异步 subdev 框架在打开节点时，会沿着设备树里的 `remote-endpoint` 去找链路另一头的 sensor；这块板 dtb 里 sensor 节点没启用/物理上没接，所以查不到 endpoint 对应的设备，返回 `-ENODEV`。日志时间戳在 `521110 s`（约 6 天 uptime），说明是**每次尝试打开节点时触发**，不是启动时的错误 —— 驱动本身是好的。

这比「板子没有摄像头」高一个层次：现在能说清**是哪一层、哪个函数、哪个错误码**报出来的。

## 7. 完整调用链（背下来就能答）

```
 用户态  video_demo.py / eval_map.py
   │  from rknnlite.api import RKNNLite   (2.3.2)
   ▼
 运行时库  librknnrt.so (7.37 MB, /usr/lib/)
   │  内含 /dev/dri 与 /dev/rknpu 两套探测逻辑 → 选中 DRM
   ▼
 系统调用  open("/dev/dri/renderD129") + DRM ioctl (GEM 创建/提交)
   │  权限：root:render crw-rw----  → 需要 render 组 + debugfs 读权限(sudo)
   ▼
 内核驱动  rknpu (builtin, CONFIG_ROCKCHIP_RKNPU=y)
   │  CONFIG_ROCKCHIP_RKNPU_DRM_GEM=y / DEBUG_FS=y
   ▼
 内存      DRM GEM → CMA 288 MB 池 → IOMMU 建立 IOVA 映射
   │  (推理日志: gem name: 3, iommu domain id: 0)
   ▼
 时钟电源  devfreq(userspace, 8 档 300M~1G) → SCMI → BL31 改 PLL
   │  pm_genpd: npu/nputop/npu1/npu2 四层，空闲 suspended
   ▼
 硬件      fdab0000.npu 三核 (--core 012)
   │  设备树描述 + OTP leakage/opp-info 体质 + npu-thermal 115°C 保护
   ▼
 结果回传  → unpack_outputs → NMS → 画框 → results/
```

一句话版本：**Python 调 rknnlite → 库通过 DRM render node 发 ioctl → builtin 的 rknpu 驱动用 GEM 分配内存并经 IOMMU 映射 → devfreq 通过 SCMI 让固件升频、power domain 上电 → 三核 NPU 执行 → 结果回传做后处理。**

## 8. 输出里 5 个「看起来像错、其实没错」

| 现象 | 真相 |
|---|---|
| `[7]` 里 `E Runtime environment is not inited…` / `None` | 脚本只构造了 `RKNNLite()` 对象就去读版本，没调 `init_runtime`。是脚本写法导致的提示，**不是环境坏了**；`2.3.2` 已正常打印 |
| `major=e2 minor=81` | `stat` 的 `%t/%T` 输出十六进制：`0xe2=226`、`0x81=129`，与 `ls -l` 的 `226,129` 一致 |
| 属性显示成 `'U   \x06'` 之类乱码 | 二进制属性（phandle/reg/clocks）被误判为字符串，不是文件损坏 |
| `cma: Reserved 32 MiB` 但 `CmaTotal 288 MB` | 有多个 reserved-memory CMA 区，dmesg 只匹配到其中一行 |
| `NPU load: Core0/1/2: 0%` + 电源域全 `suspended` | 探测时**没有在推理**，NPU 被 runtime PM 断电了，属于正常空闲态 |

另外 `CONFIG` 段输出重复了两遍，是因为脚本同时读了 `/proc/config.gz` 和 `/boot/config-*`，两个来源内容相同。

| 历史记录 | 这次探查 | 判定 |

## 10. 面试高频追问 × 答法

| 追问 | 答法要点 |
|---|---|
| 「你这驱动是模块还是编进内核的？怎么证明？」 | `CONFIG_ROCKCHIP_RKNPU=y`，`/proc/config.gz` 直接读出来；所以 `lsmod` 空、`modprobe -r` 被拒，但 `/sys/module/rknpu` 仍在 |
| 「为什么教程说找 `/dev/rknpu`，你却用 `/dev/dri/renderD129`？」 | 内核开了 `DRM_GEM=y`、`DMA_HEAP` 未开 → 驱动注册为 DRM 设备；render node 编号 = `128 + minor`，dmesg 里 `minor 1` → 129。是**厂家 BSP 编译选项差异**，不是装错驱动 |
| 「为什么要 sudo？加组不行吗？」 | `render`/`video` 组已加好，节点权限 `root:render crw-rw----`；瓶颈在 `/sys/kernel/debug/rknpu/version` 这类 root-only debugfs 文件，runtime 靠它判驱动形态（推测，未读源码证实） |
| 「模型权重怎么进 NPU 的？」 | DRM GEM 对象分配 → CMA 池出页 → IOMMU 建 IOVA 映射 → NPU DMA 直接读；推理日志 `gem name: 3, iommu domain id: 0` 佐证 |
| 「devfreq 锁频到底锁了什么？」 | 把 governor 从 `rknpu_ondemand` 改 `userspace` 并把 OPP 钉在 1 GHz（8 档 300M~1G 之一）；真实 PLL 由 SCMI 经 BL31 固件设置。不锁时叠加电源域唤醒与热区调节，101 ms 且方差巨大 |
| 「NPU 不用的时候在干什么？」 | `pm_genpd` 显示 npu/nputop/npu1/npu2 四层全 suspended，clk enable=0 —— runtime PM 把整个 NPU 断电；首次推理慢正是上电+升频+权重搬运 |
| 「OPP 档位是写死的吗？」 | 不是。`npu-opp-table` 通过 `nvmem-cells` 读 OTP 里的 `leakage`/`opp-info`（出厂按芯片体质烧录），配合 `clk_npu_pvtm` 和 115°C 的 `npu-thermal` 做闭环 |
| 「你说没摄像头，具体是哪一层报的？」 | V4L2 异步 subdev 沿 dtb 的 `remote-endpoint` 找 sensor，`rkcif_update_sensor_info` 返回 `-19 = -ENODEV`；节点和 ISP/CIF 驱动都在，只是链路另一头没设备 |
| 「CPU 侧你怎么处理频率？」 | 三个 cpufreq policy（0–3 / 4–5 / 6–7）全设 performance，分别 1.8 / 2.304 / 2.352 GHz；NPU 单独走 devfreq。两边都要锁，只锁一边会差 2.2 倍 |

### 11.1 已回填：NPU 多核调度实测（2026-11-09，B 类动作 1 + 2）

**来源**：板端 `core_scaling_bench.sh` → `results/core_scaling_summary.txt`（生成于 16:25:04）。条件与 §5 一致：NPU `userspace@1 GHz` + 三个 CPU policy 全 `performance`；`--core 0 / 1 / 2 / 012` 四组，每组 warmup 10 + 200 帧逐帧换图，`coco/val2017` 图片序列，模型仍是 5.67 MB 的 head FP16。

| core | 纯前向 平均 / P50 / P95 | 纯前向 FPS | 端到端 平均 / P50 / P95 | 端到端 FPS |
|---|---|---|---|---|
| `0` | **34.98** / 35.25 / 37.63 ms | **28.6** | **38.38** / 38.63 / 41.17 ms | **26.1** |
| `1` | 36.48 / 36.26 / 39.03 ms | 27.4 | 40.04 / 39.61 / 42.80 ms | 25.0 |
| `2` | 35.52 / 35.75 / 38.88 ms | 28.2 | 38.93 / 39.08 / 42.77 ms | 25.7 |
| `012` | 35.64 / 35.44 / 38.77 ms | 28.1 | 39.16 / 38.79 / 42.62 ms | 25.5 |

**结论：三核对单帧 YOLOv8n 没有加速。** 三个单核之间本来就有 34.98~36.48 ms 的固有波动（约 4.3%），而三核 `012` 的 35.64 ms 正好落在这个区间内 —— 相对**最快**的单核 `0` 反而慢 **0.66 ms（+1.9%）**，相对三个单核的均值 35.66 ms 几乎持平。也就是说，开三核带来的差异小于测量自身的核间波动，属于「无加速 + 一点调度开销」，不是性能优化手段。

这同时解释了报告 §3.1 的数字：`core=012` 这次 35.64 ms，另一次跑 `video_demo.py` 得到 35.82 ms，两次波动 <1%，跨端结论稳定；**§3.1 里的 `core 012` 只是测量时用的默认配置，不是加速来源**。

**推理中负载采样（248 行，每 0.2 s 一条）**：

| 证据 | 实测 | 说明 |
|---|---|---|
| 电源域 | 前 3 条 `nputop off-0 / npu off-0` → 末尾 `nputop on / npu on` | ✅ 直接坐实 §5 第三层：runtime PM 空闲断电、推理上电 |
| 三核负载 | 末尾样本 `Core0: 52%, Core1: 4%, Core2: 5%` | 即便 `--core 012`，负载也几乎全压在 Core0，另两核只有零星活动 |
| 非零出现次数 | `Core0: 112 / Core1: 117 / Core2: 116`，三个核都被点亮过 | ⚠️ 采样**跨了四组配置**（`--core 1` 那组点亮 Core1、`--core 2` 点亮 Core2），所以「三核都出现过非零」只能证明四组分别点亮过不同核，**不能**证明同一帧被拆到三核并行 |

**为什么三核没用**：`core_mask` 的语义是「允许 runtime 把任务调度到哪些核」，不是「把一帧推理拆成三份并行算」。5.67 MB 的 YOLOv8n、batch=1、单帧串行，粒度太细，一帧内部可并行的部分不够支付跨核同步/搬运开销，runtime 实际仍集中在单核上执行（末尾 52% vs 4%/5% 就是证据）。要真正吃满三核，得靠**多路流 / 多模型实例并发**或 batch 推理，而不是给单帧换 `core_mask`。

> **面试可用**：「我做过 NPU 多核扩展性实测：单核 0/1/2 与三核 012 各 200 帧，发现三核对 YOLOv8n 这种小模型单帧推理没有加速，反而比最快单核慢约 1.9%；配合推理中采 `rknpu/load`，看到负载集中在 Core0（52% vs 4%/5%），判断 `core_mask` 是调度范围而非帧内并行多核。同时采到 `pm_genpd` 从 `off-0` 变 `on`，佐证了 runtime PM 的上电行为。」—— 这条的价值是**实测证伪 + 定位到负载分布**，比空喊「配置三核 NPU 调度」硬得多。

> ⚠️ **边界**：只测了 `0 / 1 / 2 / 012` 四组，`video_demo.py` 没有双核选项；没测多实例并发，也没测 batch>1。结论只适用于「单模型、单帧、串行」这个场景，不能推广成「RK3588 三核没用」。

> 先按四组记：`DT/U-Boot/BL31/SCMI` 启动链、`DRM/GEM/CMA/IOMMU` 内存链、`devfreq/OPP/genpd/PVTM` 频率电源链、`NPU/RKNN/ONNX/PTQ` AI 链 —— 正好对应第 7 节那条八层调用链。

| 缩写 | 全称 | 人话 / 在这块板上指什么 |
|---|---|---|
| **SoC** | System on Chip，系统级芯片 / 片上系统 | CPU+GPU+NPU+ISP+VPU+IOMMU 全在一颗硅片上；**RK3588 是 SoC 型号，AIO-3588Q 才是板卡型号** |
| **BSP** | Board Support Package，板级支持包 | 让 OS 能在这块具体板子上跑起来的适配软件：U-Boot + 固件 + 打过补丁的内核 + DTB + 板级驱动；通用内核不知道 NPU 挂哪个地址 |
| **SDK** | Software Development Kit | 范围比 BSP 大：BSP + 交叉工具链 + 文档/示例 + 烧录工具（`rk3588_linux6.1_release_...xml` 就是 SDK manifest） |
| **主线 Linux / mainline** | kernel.org 官方内核树 | Linus 维护、未经板卡厂打补丁的源码（含各 LTS 分支）。本板是**基于 6.1 LTS 的厂商 BSP 内核**，版本号像主线、内容差很多（大量 SoC 驱动只存在于厂商分支） |
| **LTS** | Long-Term Support | 长期维护版本，6.1 是其中之一；厂商常选 LTS 做基线再叠自己的补丁 |
| **dmesg** | diagnostic message | 读内核 **ring buffer**（开机以来 `printk` 日志）的命令，时间戳单位是「开机后秒数」，重启清空；`[drm] Initialized rknpu ... minor 1`、`rkcif ... -19` 都从这里来 |

| **GEM** | Graphics Execution Manager | DRM 的内存对象管理；权重就装在 GEM 对象里（`gem name: 3`） |

| **devfreq / cpufreq** | Device / CPU Frequency | 调 NPU / CPU 频率的内核框架 |
