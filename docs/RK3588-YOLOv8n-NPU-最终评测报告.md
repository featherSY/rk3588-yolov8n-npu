# RK3588 YOLOv8n NPU 部署 · 最终评测报告

> 结论：**INT8 主干 + FP16 检测头的混合量化方案，在全量 COCO val2017（5000 张）上相对 x86 FP32 基线只掉 0.98 点（mAP@0.5）/ 1.25 点（mAP@0.5:0.95），达到 <2 点目标；延迟 33.30 ms / 30.0 FPS，仅比全 INT8 慢 4.62 ms，速度优势保持。** 定为默认部署配置。  
> 误差定位结论：INT8 掉点几乎全部来自 `model.22` 检测头内部，其中 **cv2 + DFL 框回归分支**是主要来源；分数输出的 1/255 台阶不是主因（head FP16 输出仍带台阶，精度却几乎无损）。  
> **跨端结论（§3.1，2026-11-09 补测）**：同口径 200 帧逐帧实测下，RK3588 纯前向 35.82 ms / 27.9 FPS、端到端 39.44 ms / 25.4 FPS，对比 x86 ORT FP32 的 37.89 ms / 26.4 FPS、42.20 ms / 23.7 FPS，**板端略快 5~7%**。板端跑的是 5.67 MB 的 INT8+FP16 混合量化模型，对手是 12.85 MB 的 x86 FP32 —— 项目最初「同一 YOLOv8n，x86 与 RK3588 差多少」的问题至此有确定答案。

## 3. 速度结果（板端各方案内部比较）

> 本表只比较板端各方案：单图重复 200 帧、仅计 `rknn.inference()`、NPU 锁 1 GHz。早期把 x86 26.5 ms 与这些数字放同一列的做法因口径不齐已废弃；**跨端同口径对比见 §3.1**。`core` 列只是运行时的核配置（`012` 为默认），**不是加速手段** —— 四组实测见 §3.1 末尾补充段，结论是三核无加速。

| 方案                   | core | 平均延迟         | FPS      | 相对全 INT8        |
| -------------------- | ---- | ------------ | -------- | --------------- |
| RK3588 全 FP16        | 012  | 46.75 ms     | 21.4     | 1.63×（慢）        |
| RK3588 全 INT8 (2out) | 012  | **28.68 ms** | 34.9     | 1.00×           |
| RK3588 head FP16     | 012  | **33.30 ms** | **30.0** | 1.16×（+4.62 ms） |

head FP16 实测明细：**平均 33.30 ms / P50 31.80 / P95 41.59 / 最快 27.76**（warmup 10 + 200 帧，仅 `rknn.inference()`，NPU 1 GHz + CPU performance）。

**"保持速度优势"判定：达标。** 只把检测头（18 个卷积）转 FP16、主干仍 INT8，代价 **+4.62 ms（+16.1%）**，换来 **+7.00 / +8.90 点 mAP**；相对全 FP16 仍快 **13.45 ms（−28.8%）**。以每毫秒换回的精度计，这是本轮性价比最高的方案。

### 3.1 跨端同口径对比（P0 收口 · 2026-11-09）

**为什么要重做**：早期 x86 26.5 ms（端到端）与板端 33.30 ms（纯前向）口径不齐，无法回答项目最初的问题；x86 侧另有 27.0 / 31.0 ms 两个来自不同脚本、线程数与 ORT 版本的数字，均不可复现。故按「口径明确、线程公开、两端同法」重建基线。

**测量条件（两端一致）**：warmup 10 + 200 帧、逐帧换图、conf 0.25 / nms 0.45、letterbox 640；分别计时纯前向（ORT `sess.run()` / `rknn.inference()`）与端到端（前处理 + 前向 + 后处理），绘制与写视频不计入计时。

| 项  | x86 ORT FP32                                                                               | RK3588 head FP16                                                                              |
| -- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 环境 | WSL2 Ubuntu，Core Ultra 7 255HX（`nproc=6`，WSL 仅暴露 6 核），ORT **1.26.0**，`threads=0`（默认用满 6 核） | `core 012`（默认核配置，**非加速手段**，见本节末尾补充段），NPU 锁 1 GHz + CPU performance，lite2 2.3.2 / driver 0.9.8 |
| 模型 | `yolov8n.onnx` FP32，**12.85 MB**                                                           | `yolov8n_head_fp16.rknn`，**5.67 MB**（INT8 主干 + FP16 head）                                     |
| 输入 | `calib200` 200 张                                                                           | `val2017` 前 200 张                                                                             |

| 口径      | x86                                           | RK3588                                            | 差值                    |
| ------- | --------------------------------------------- | ------------------------------------------------- | --------------------- |
| **纯前向** | 37.89 ms（P50 37.17 / P95 44.33）/ **26.4 FPS** | **35.82 ms**（P50 35.69 / P95 38.23）/ **27.9 FPS** | 板端快 **2.07 ms（5.5%）** |
| **端到端** | 42.20 ms（P50 41.48 / P95 49.08）/ **23.7 FPS** | **39.44 ms**（P50 38.98 / P95 41.85）/ **25.4 FPS** | 板端快 **2.76 ms（6.5%）** |
| 前后处理开销  | 2.68 + 1.62 = 4.30 ms                         | 3.62 ms                                           | 同量级                   |

**结论**：在 x86 仅 6 核可用、且跑 FP32 12.85 MB 模型的前提下，RK3588 以 5.67 MB 的 INT8+FP16 混合量化模型做到**略快 5~7%**（纯前向 27.9 vs 26.4 FPS、端到端 25.4 vs 23.7 FPS）。不是数量级差距，但对手是笔记本高端 CPU、板端是边缘 SoC，能效比优势显著 —— 这也是「CPU 上 INT8 加速上限仅 1.05×，量化收益需要专用加速器」这条动机的实测闭环。

**两个不能混用的数字**：`33.30 ms` 是单图重复、无 I/O 与绘制的纯推理基准；`35.82 ms` 是逐帧完整流水线（换图、letterbox、NMS、绘制、写视频）下的纯前向，高 2.52 ms（+7.6%）来自 I/O 与 CPU/内存带宽争用。两者各自有效，**跨端对比只用 35.82 / 39.44 这一组**。

**历史数字处置**：26.5 / 27.0 / 31.0 ms 与 37.8 FPS 统一加注「早期测量，脚本 / 线程 / ORT 版本不明，不可复现」，保留在 README 与本表作为过程记录，不再用于任何结论或加速比计算。

**补充：`core 012` 不是加速来源（2026-11-09 多核实测）**：另跑 `--core 0 / 1 / 2 / 012` 四组各 200 帧（同一锁频条件、同一 `val2017` 图片序列、同一 5.67 MB 模型），纯前向平均分别为 `34.98 / 36.48 / 35.52 / 35.64 ms`，端到端 `38.38 / 40.04 / 38.93 / 39.16 ms`。三核 `012` 落在三个单核的固有波动区间（34.98~36.48 ms）内，比最快单核 `0` 反慢 **0.66 ms（+1.9%）**；推理中采 `rknpu/load` 显示负载集中在 Core0（`52%` vs `4% / 5%`），`pm_genpd` 的 `nputop` / `npu` 从 `off-0` 变 `on`。结论：5.67 MB 小模型 + batch=1 单帧串行下，`core_mask` 的语义是「允许调度到哪些核」而非「把一帧拆到三核并行」，因此**三核没有加速**；§3 表格与本节环境行里的 `012` 仅为测量时的默认配置，**不作为性能亮点**。完整数据、负载采样与机制解释见《RK3588-板级系统与驱动认知笔记》§11.1。

## 4. 误差定位：四个假设的完整验证链

> 本节为 §2 筛选阶段（500 张子集）的误差归因，表中数值均为该口径；全量复评见 §2.1，结论方向一致。

掉点 10.6 点远超 YOLOv8n INT8 的正常水平（1~3 点），因此逐层排除：

| 假设                          | 干预手段                                    | 结果                                     | 判定       |
| --------------------------- | --------------------------------------- | -------------------------------------- | -------- |
| ① 框坐标输出量程过粗（0~640 压进 256 档） | boxes 分支插 `Div(8)` 压缩量程，评估时乘回           | 0.4629 / 0.2788                        | ❌ 证伪     |
| ② cv3 分类分支权重有离群值            | 混合量化，仅 15 个 cv3 张量转 FP16                | 0.4626 / 0.2806                        | ❌ 证伪     |
| ③ 分数 1/255 台阶破坏 NMS 排序      | (a) 出口改 sigmoid 前 logits；(b) 输出张量设 FP16 | (a) 0.4629 / 0.2787；(b) 台阶吻合 0.999，未生效 | ❌ 证伪     |
| ④ **误差在 cv2 + DFL 框回归分支内部** | 整个 `model.22` 的 51 个合法张量转 FP16          | **0.5299 / 0.3745**                    | ✅ **成立** |

**关键反证**：方案 8 的输出层仍是 INT8（`P10=0.0039=1/255`、台阶吻合度 0.999），分数台阶完全没变，mAP 却几乎回到 FP32。这直接排除了"分数台阶是主因"，也解释了为什么 logits 路线无效。

**量化台阶的数学根源**：`yolo_out_1` 的 scale = `0.9833/255 = 0.0038561`，量程 [0, 0.983]，256 档，分数分辨率锁死为 1/255。FP32 有 66 702 个不同分数，INT8 只有 147 个且全部落在台阶上。这是 RK3588 输出层 INT8 的固有属性，**改 cfg 无效**。


**误差在框分支的物理表现**：框面积中位数系统性偏小 11.6%，小目标类掉点最重。`DFL` 的 softmax + 加权求和在 INT8 下累积误差，直接扭曲框的位置与尺寸；把 head 转 FP16 后该累积误差消失。

## 5. 关键工程结论（踩过的坑，可复用）

1. **venv 隔离**：`rknn_toolkit2==2.3.2` 只装在 `~/rknn-env`，WSL 下必须先 `source ~/rknn-env/bin/activate`，用 `python` 而非 `python3`。
2. **校准集路径**：rknn 对 dataset txt 中的相对路径按 `$HOME` 解析而非 CWD，必须写 `os.path.abspath()`。
3. **dtype 支持**：RK3588 后端只真正支持 **FP16 / INT8**。`w16a16i` 等 int16 是 API 占位，会 `Lut fuse dtype not support` + `Illegal instruction (core dumped)`；`w8a16` 仅 RK3566/3568 支持。
4. **混合量化 cfg 认"张量名"不认"节点名"**：`custom_quantize_layers` 必须是 `/model.22/cv3.0/.../Conv_output_0` 这类输出张量名，写 `/model.22/cv3.0/.../Conv` 会报 `Invalid operands name`。唯一可靠来源是 cfg 自身的 `quantize_parameters` 段。
5. **非法 operand**：`Constant_*`（权重常量）、`images`（网络输入）、`*_int8`（量化变体）、`*_2mul_i1`（二元 op 常量操作数）都不能进 `custom_quantize_layers`，否则 step2 直接拒收。
6. **输出层 dtype 改不动**：`custom_quantize_layers` 只对**中间层**有效；模型输出张量的 dtype 在 `build` 阶段固化，`hybrid_quantization_step2` 改不了顶层输出。设置后仍输出 `float32` 且台阶吻合 0.999。
   |   |   |   |
   | - | - | - |
7. **判断量化是否生效看台阶吻合度，不看 dtype**：runtime 输出永远是反量化后的 `float32`；用 `|v×255 − round(v×255)| < 0.02` 的占比判定是否仍在 1/255 网格上。
8. **体积判据**：`.rknn` 体积只由**有权重的层**决定，DFL/Concat/Reshape 等无权重层转 FP16 不涨体积。4.74 MB（全 INT8）→ 5.25 MB（cv3 FP16）→ **5.67 MB（cv2+cv3 全 FP16）** 才是正确标定。
9. **`--box-scale 8`**：boxes 分支插了 `Div(8)`（输出 max≈80），评估必须乘回 8，否则框坐标缩成 1/8、mAP 崩到接近 0。**CLI 可视化同理**：`eval_map.py` 带了该参数所以 mAP 正常（0.5299），但 `infer_image.py` 原先没带，0~80 的坐标被 letterbox 的 `top=80` padding 减成负数再 clamp 到 0，所有框退化成 `y1=y2=0` 的贴顶细线 → 检测到 7 个目标却画不出框。**评估脚本与推理脚本的坐标还原必须同步**，现已给 `infer_image.py` 加 `--box-scale auto`（按 `max<120` 自动乘 8）。
10. **多余输出**：拆分后的模型带 3 个输出，其中 `[1,84,8400]` 是未使用的原始 concat 输出，每次推理白搬约 2.8 MB，可在收尾优化时删除。
11. **模拟器限制**：PC 模拟器不认 `core_mask`，`init_runtime()` 不要传参；`load_rknn` 后无法在 PC 直接推理，输出体检必须上板。
12. **step1 产物位置**：`hybrid_quantization_step1` 把 `.model/.data/.quantization.cfg` 写在 CWD，复用时可用 `--skip-step1`。
13. **step2 签名**：2.3.2 实际为 `hybrid_quantization_step2(model_input, data_input, model_quantization_cfg)`，无 `model_script` 参数；`The node ... is specified repeatedly` 是 WARN，可忽略。

## 6. 部署选型建议

| 场景 | 推荐方案 | 精度 | 速度 | 体积 |
| --- | --- | --- | --- | --- |
| **精度 + 速度均衡（默认推荐）** | **INT8 主干 + FP16 head** | **全量 0.4889 / 0.3426**（掉 0.98 / 1.25 点，§2.1） | **33.30 ms / 30.0 FPS** | **5.67 MB** |
| x86 FP32 对照 | ORT FP32 基线 | 全量 0.4987 / 0.3552 | 37.89 / 42.20 ms（§3.1 同口径） | 12.26 MB |
| 精度绝对优先 | 全 FP16 | 500 张子集 0.5417 / 0.3909（≈无损） | 46.75 ms / 21.4 FPS | 较大 |
| 速度绝对优先、可接受漏检 | 全 INT8 | 500 张子集 0.4599 / 0.2855 | 28.68 ms / 34.9 FPS | 4.74 MB |

> 带「500 张子集」标注的两行仅为 §2 筛选阶段数据，不与全量行混用。
